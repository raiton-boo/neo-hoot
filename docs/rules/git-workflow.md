# 🌳 Git運用ルール (neo-hoot)

本ドキュメントは `~/dev/rules` にある個人の標準ルール（BRANCHING.md / COMMIT-MESSAGE.md / PR.md / ISSUE.md）を
あくまで参考としつつ、neo-hoot固有の事情（pnpm + Turborepoによるモノレポ構成、api/webの関心ごと分離、ソロでの学習用ポートフォリオ開発）に
合わせて独自にアレンジしたものです。

## 1. ブランチ戦略（2層構造）

`main`から直接、機能ブランチを切って作業する2層構造を採用する。ソロでの学習用ポートフォリオ開発であり、複数人の作業をまとめてから`main`に反映する必要が無いため、間に統合ブランチは置かない（常にSquash and Mergeなので、直接`main`へPRしても履歴はきれいなまま保たれる）。

```
main
 ├─ api/feat/result-aggregation   （バックエンドの機能ブランチ）
 ├─ api/fix/socket-reconnect
 ├─ web/feat/quiz-room-creation   （フロントエンドの機能ブランチ）
 ├─ web/fix/login-validation
 ├─ chore/turborepo-setup         （リポジトリ全体に関わる機能ブランチ）
 └─ ci/add-github-actions
```

> Gitはブランチの「派生元」情報を名前として保持しないため、`feat/xxx`だけでは`git branch -a`で見たときにapi由来かweb由来か判別できない。関心ごとをブランチ名自体に埋め込むことで一覧性を確保する。

> **関心ごとを表すために`api`や`web`という名前のブランチ単体を作ってはいけない。** Gitはブランチ名の`/`をディレクトリ構造として扱うため、`api`というブランチと`api/feat/xxx`というブランチは共存できない（`refs/heads/api`が既にファイルとして存在する状態で、`refs/heads/api/feat/xxx`というディレクトリを作ろうとしてエラーになる）。関心ごとは、あくまで機能ブランチ名の先頭に付ける接頭辞（`api/`, `web/`）としてのみ使う。

- **`main`**: 常にデプロイ可能な状態を保つ。直接の`push`は厳禁。
  - 【例外】プロジェクトの初期セットアップ時（最初のコミット、フレームワークの初期生成など）は直接pushしてよい。
- **`packages/`配下**（db, types, socket, queueなど）の変更は、主に利用する側の接頭辞（`api/`または`web/`）を付けた機能ブランチに含める。

### 機能ブランチの命名規則

- **`api`または`web`に関わる機能ブランチ**:

  ```
  関心ごと/接頭辞/短い英単語（ケバブケース）　※Issue番号は含めない
  ```

  - 良い例: `api/feat/result-aggregation`, `web/fix/login-validation`
  - 悪い例: `feat/add-new-endpoint-for-aggregating-quiz-results`（関心ごとが無い、長すぎる）

- **リポジトリ全体に関わる機能ブランチ**（`api`/`web`どちらにも属さないもの）:

  ```
  接頭辞/短い英単語（ケバブケース）
  ```

  - 例: `chore/turborepo-setup`, `ci/add-github-actions`

### 接頭辞（プレフィックス）一覧

接頭辞そのものは共通。関心ごとブランチ配下では先頭に`api/`または`web/`を付ける。

| 接頭辞          | 用途                                             | 具体例（関心ごと配下の例）             |
| :-------------- | :----------------------------------------------- | :------------------------------------- |
| **`feat/`**     | 新機能の追加                                     | `api/feat/result-aggregation`          |
| **`fix/`**      | バグの修正                                       | `web/fix/socket-reconnect`             |
| **`hotfix/`**   | 本番環境（`main`）の緊急バグ修正                 | `api/hotfix/payment-crash`             |
| **`refactor/`** | リファクタリング（機能追加やバグ修正を含まない） | `api/refactor/user-service`            |
| **`chore/`**    | パッケージ追加、ビルドプロセスの変更など雑務     | `chore/update-deps`（リポジトリ全体）  |
| **`docs/`**     | ドキュメント（README等）の追加・修正             | `docs/update-readme`（リポジトリ全体） |
| **`test/`**     | テストコードの追加・修正                         | `test/auth-logic`                      |
| **`ci/`**       | CI/CD（GitHub Actions等）の設定変更              | `ci/add-github-actions`                |

## 2. Issue運用

- 原則として、**必ずIssueを作成してからブランチを切る**。
  - 学習ポートフォリオとして「設計→タスク分解→実装」の過程を記録として残す目的も兼ねる。
- **タイトル命名規則**: `[関心ごと] 簡潔なタスク名`（typeの接頭辞は付けない）
  - 関心ごとはブランチ戦略に対応する `api` / `web` を基本とし、リポジトリ全体に関わるものは `repo` とする。
  - 例: `[api] クイズ結果集計エンドポイントの実装`, `[web] クイズルーム作成画面のUI実装`, `[repo] Turborepoの初期セットアップ`
- **1 Issue ＝ 1タスク**。作業が多岐にわたる場合はタスクを分割して別Issueにする。
- `gh issue create` には必ず `--assignee "@me"` を付ける（自動アサインの仕組みはない）。

### Issue本文テンプレート

`.github/ISSUE_TEMPLATE/`は設置せず、このドキュメントに書いた内容をそのまま手動でコピーして使う。

```markdown
## 概要・目的

<!-- 何を、なぜ実装/変更するのか -->

## やること

- [ ] 〇〇のUI実装
- [ ] APIのレスポンス処理を追加

## 受け入れ条件

- 〇〇ボタンを押すと正常にログイン処理が行われること
- エラー時に適切なエラーメッセージが表示されること

## 備考・補足（あれば）

<!-- 参考資料、デザイン案のリンク、関連するコードなど -->
```

### ラベル運用（任意）

| ラベル名   | 用途・意味                                       |
| :--------- | :----------------------------------------------- |
| `feature`  | 新機能の追加・仕様変更                           |
| `fix`      | バグ・不具合の修正                               |
| `refactor` | 機能追加・バグ修正を伴わないコードの整理         |
| `docs`     | ドキュメントの追加・修正                         |
| `chore`    | ビルド設定やライブラリ更新などその他の作業       |
| `hotfix`   | 本番障害など、最優先で即時対応が必要な緊急タスク |

## 3. コミットメッセージ規約（Conventional Commits簡略版）

### 基本フォーマット

```
<type>: <subject>
```

- **`type`**: コミットの種類（ブランチの接頭辞と完全に一致させる）
- **`subject`**: 変更内容の簡潔な要約（日本語でOK）
- `:` の後ろには必ず半角スペースを1つ空ける

### type一覧

| Type            | 用途                                       | 例                                       |
| :-------------- | :----------------------------------------- | :--------------------------------------- |
| **`feat:`**     | 新機能の追加                               | `feat: クイズ結果集計APIを実装`          |
| **`fix:`**      | バグ修正                                   | `fix: Socket再接続時のルーム重複を修正`  |
| **`hotfix:`**   | 本番の緊急バグ修正                         | `hotfix: 決済APIのエラーを修正`          |
| **`refactor:`** | リファクタリング（機能追加やバグ修正なし） | `refactor: ログインロジックの共通化`     |
| **`chore:`**    | ツール設定、パッケージ更新、雑務           | `chore: 依存パッケージのアップデート`    |
| **`docs:`**     | ドキュメントの追加・修正                   | `docs: セットアップ手順を追記`           |
| **`test:`**     | テストの追加・修正                         | `test: 集計ロジックのテストを追加`       |
| **`ci:`**       | CI/CD（GitHub Actions等）の変更            | `ci: 本番デプロイ用のワークフローを追加` |

### ベストプラクティス

- **1コミット＝1つの関心事（Single Concern）**: 複数の関心事を1つのコミットに混ぜない。
- **基本は1行で完結させる**: 背景や詳細な理由はPRの概要欄に記載する。
- **Issueとの紐付け**: 通常はPR本文に `Closes #12` と書く。PRを経由しない直push時のみ、コミットメッセージ末尾に含めてよい。
- **`git checkout` の使用は禁止**: ブランチ切り替えには `git switch`、ファイルの復元・取り消しには `git restore` を使用する。

## 4. プルリクエスト規約

### 基本ルール

- **1 PR ＝ 1 目的**: 「新機能の追加」と「無関係なリファクタリング」は別のPRに分ける。
- **タイトル**: コミットメッセージ規約と同様に `type: 概要` の形式にする（scopeなし）。
  - 例: `feat: クイズ結果集計APIを実装`
- **Assigneesに必ず自分自身（`@me`）を設定**する。`gh pr create` には必ず `--assignee "@me"` を付ける（自動アサインの仕組みはない）。
- **セルフレビューの徹底**: レビュー前に必ず「Files changed」を確認し、不要なファイルやデバッグ用コード（`console.log` など）が含まれていないかチェックする。
- **マージ方式**: 常にSquash and Merge。GitHubリポジトリ設定側で「Allow squash merging」のみを許可し、他の方式は選べないようにする（ドキュメント側でのルール運用は不要）。

### マージフロー

機能ブランチ（`api/feat/xxx`, `web/feat/xxx`, `chore/xxx`など）から、直接`main`へPRを出す。

### PR本文テンプレート

`.github/pull_request_template.md`は設置せず、このドキュメントに書いた内容をそのまま手動でコピーして使う。ブランチ名・コミット一覧・変更ファイルはGitHubのPR画面（ブランチ表示・Commitsタブ・Files changedタブ）で自動的に見えるため書かない。

```markdown
## 概要

<!-- 何を、なぜ変更したか -->

## 動作確認

- [ ] Linter・自動テストをクリアした
- [ ] ローカル環境で〇〇が正常に動作することを確認した

## 関連Issue

<!-- Closes #xx -->
```
