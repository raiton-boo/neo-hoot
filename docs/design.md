# 🎨 デザインシステム (neo-hoot)

ネオブルータリズム（POP寄り）のデザイン言語を定義する。ここで決めた内容を元に`docs/wireframes/`でワイヤーフレームを作成し、実装時は`apps/web`のTailwind設定に反映する。

## 1. ネオブルータリズムとは・今回の方向性

ネオブルータリズムは、太い枠線・ずれたベタ塗りの影（ぼかしなし）・高彩度の色面を特徴とするデザインスタイル。「あえて洗練させすぎない」荒削りな存在感が特徴。

今回は**POP寄り**（コントラストの強い原色系だが、遊び心のある明るい配色、角を少し丸めた親しみやすさ）に振る。完全な無彩色・鋭角のみのストイックな方向にはしない。

## 2. カラーパレット

### ライトモード（デフォルト）

| 用途                   | 変数名              | 値                              |
| :--------------------- | :------------------ | :------------------------------ |
| 背景                   | `--color-bg`        | `#FFFBEA`（生成り・クリーム色） |
| サーフェス（カード等） | `--color-surface`   | `#FFFFFF`                       |
| 枠線・文字             | `--color-ink`       | `#0A0A0A`                       |
| プライマリ（黄）       | `--color-primary`   | `#FFD60A`                       |
| セカンダリ（ピンク）   | `--color-secondary` | `#FF3D8A`                       |
| アクセント（青）       | `--color-accent`    | `#3D5AFF`                       |
| 成功（緑）             | `--color-success`   | `#00C853`                       |
| 危険（赤）             | `--color-danger`    | `#FF3B30`                       |

### ダークモード

| 用途                 | 変数名            | 値                                                       |
| :------------------- | :---------------- | :------------------------------------------------------- |
| 背景                 | `--color-bg`      | `#16121F`（ネイビー寄りの濃紫）                          |
| サーフェス           | `--color-surface` | `#221C33`                                                |
| 枠線・文字           | `--color-ink`     | `#F5F5F0`                                                |
| その他のアクセント色 | —                 | ライトモードと同じ値を使用（十分な彩度・明度があるため） |

ニュートラルなグレー（`#121212`系）や漆黒（`#0A0A0A`系）も候補として比較したが、POP寄りのネオブルータリズムという方向性には「ネイビー」が最も合っていたため採用した。

## 3. タイポグラフィ

- **見出し（英数字）**: `Paytone One`。丸みがあり親しみやすい、POP寄りのネオブルータリズムに合う極太の見出し用フォント。
- **見出し（日本語）**: 別途、太めの日本語フォント（例: `Noto Sans JP` Bold）を組み合わせる。`Paytone One`は欧文専用のため、日本語部分では反映されない。
- **本文**: 可読性重視のサンセリフ体（例: `Inter`、またはシステムフォント）。
- 見出しは基本**大きく・太く**、余白を詰め気味にしてインパクトを出す。

候補として`Space Grotesk`, `Fredoka`, `Titan One`, `Luckiest Guy`, `Bangers`も比較したが、POPさと視認性のバランスから`Paytone One`を採用した。

## 4. コンポーネントの基本ルール

| 要素                       | ルール                                                                                                    |
| :------------------------- | :-------------------------------------------------------------------------------------------------------- |
| **枠線**                   | `3px solid var(--color-ink)`。細い枠線は使わない。                                                        |
| **影**                     | ぼかしなしのオフセット影: `4px 4px 0 var(--color-ink)`。光源を意識したリアルな影ではなく、記号的な影。    |
| **角丸**                   | `8px`〜`12px`程度の控えめな丸み（完全な鋭角にはしない。POP寄りのため）。                                  |
| **押下時のフィードバック** | ボタン等を押した際、影を`2px 2px 0`に縮めつつ要素を`2px, 2px`分ずらす。「実際に沈み込んだ」ように見せる。 |
| **色の塗り方**             | グラデーション・半透明は使わない。ベタ塗りのみ。                                                          |

## 5. ダークモードの切り替え方針

- OSの設定（`prefers-color-scheme`）に追従することを基本としつつ、ユーザーが手動で切り替えられるトグルも用意する。
- 色の意味（プライマリ＝黄、成功＝緑、など）はライト/ダークで変えない。背景・枠線・文字色のみ反転させる。

## 6. アクセシビリティ上の注意

- 色だけで正誤を伝えない（アイコンや文言も併用する）。参加者が回答の正誤を確認する画面などで特に注意する。
- 枠線・影を多用するデザインのため、コントラスト比は自然に確保しやすいが、パステルカラーは使わず、彩度・明度のはっきりした色のみを採用する。

## 7. 実装時のTODOメモ

- **参加⇔ホスト切り替えのアニメーション**: `docs/wireframes/`のワイヤーフレームでは簡易的なCSSアニメーション（登場時のフェード＋スライド）のみ。本実装（`apps/web`）では`Framer Motion`の`AnimatePresence`を使い、タブ切り替え時にもっと滑らかな遷移（クロスフェードやスライド）を実装する。
- **共通ヘッダーのユーザーメニュー**: PC/スマートフォンでの挙動・デザインは未確定（例: PCはホバーで開くドロップダウン、スマホはタップでボトムシート等）。実装フェーズで改めて決める。
- **参加用URLのハードコード禁止**: ワイヤーフレームでは`neo-hoot.app/join`という文字列を直接書いているが、これは環境（ローカル開発・本番等）によって実際のドメインが変わる。本実装では`window.location.origin`など、実行時の環境から動的に取得した値を表示する（`coding-style.md`の「機密情報・環境依存値のハードコード禁止」の方針にも合わせる）。

## 8. 共通ヘッダー（`.app-header`）を入れる画面の方針

- **入れる（管理画面系）**: クイズ一覧、クイズ編集など、ホストが自分のペースで操作する画面
- **入れない（ライブ進行画面）**: ロビー、出題中、設問結果、最終結果など、プロジェクター等に映して参加者全員が見る画面。ホスト個人のナビゲーション要素は不要かつ邪魔になるため、最小限の表示にする

## 9. QRコードの参加導線（サイト内スキャン vs 外部読み取り）

参加画面の「QRコードをスキャン」機能は、読み取り方法によって挙動を分ける。

- **外部（OSのカメラアプリ等）で読み取った場合**: URLに`?room=xxxx`が付いた状態でブラウザが新規にページを開く。ページ読み込み時にクエリパラメータからルームコードを取得し、入力欄に自動反映する（ワイヤーフレームで動作確認済み）。
- **サイト内（参加画面の「QRコードをスキャン」ボタン）で読み取った場合**: ページ遷移・リロードを伴わず、カメラ映像をその場（モーダル等）で表示し、読み取り結果を直接JavaScriptで入力欄に反映する想定。ページ遷移が発生しない分、より滑らかな体験にする。

## 10. 共通UIコンポーネント候補（実装フェーズで検討）

ワイヤーフレームを作る中で、複数画面で似た役割を持つパーツがいくつか見つかった。実装時にReactコンポーネントとして共通化するかどうかは、そのフェーズで改めて判断する。

- **「〇〇を待っています」系のステータス表示**（パルスドット＋文言）: ホストの`lobby.html`（「参加者を待っています」）と参加者の`lobby-wait.html`（「ホストが開始するまでお待ちください」）。文言はそれぞれの立場で異なるが、視覚的なパターン（パルスドット＋テキスト）は共通化できそうな候補。

## 11. 参加者チップの「接続中→参加確定」2段階アニメーション

参加者がルームに入ってきた瞬間に名前入りのチップがいきなり出現すると唐突なので、以下の2段階にする。

1. **接続中**: 名前がまだ確定する前に、まず中身のないプレースホルダーのチップを表示し、薄く点滅させる（`.participant-chip.connecting`）
2. **参加確定**: サーバー側で参加者情報が確定した時点で、プレースホルダーを実際の名前に差し替え、ポップイン（拡大しながらフェードイン）させる

`docs/wireframes/host/lobby.html`でJavaScriptによる疑似デモを実装済み。本実装ではSocket.ioのイベントを使って、この2段階を次のように対応させる。

- **接続中**: 参加者のクライアントがルームのSocket.io接続を確立し、`join-room`イベントをサーバーへ送った直後。サーバーはまだニックネームの検証・DB保存が終わっていないタイミングで、先に`participant:connecting`のようなイベントをホスト側へブロードキャストし、プレースホルダーを表示させる。
- **参加確定**: サーバー側でニックネームの検証・`Participant`レコードの保存が完了した時点で、`participant:joined`イベント（確定した名前を含む）をホスト側へブロードキャストする。ホストはこれを受けてプレースホルダーを実際の名前に差し替える。

**注意**: ローカルネットワークでは接続からDB保存までが一瞬で終わるため、上記の2イベントがほぼ同時に届き、「接続中」状態がほとんど見えない可能性がある。体感できるアニメーションにしたい場合は、「接続中」状態を意図的に一定時間（例: 300〜500ms）は表示し続ける、というUI側の最低表示時間を設ける手法も検討する。

## 13. ロビー画面の参加者一覧レイアウト

`host/lobby.html`の参加者チップは、**固定幅（100px）のチップを10個並べた分だけの幅にコンテナを制限し、それを超えたら自然に折り返す**方式にする（「10人ごとに1行」で揃う）。チップ幅100px・ギャップ0.75rem(12px)で、コンテナの`max-width`は`100px * 10 + 12px * 9 = 1108px`。

- 最初は「常にCSS Gridで10列」という実装を試したが、参加者が10人未満のときに余った列が空白として幅を取ってしまい、画面を無駄に広く使ってしまう問題があった。チップを固定幅にしてコンテナ幅を制限する方式に変更し、これを解消した。
- **長い名前への対応**: 最初はチップ内で2行に折り返す方式を試したが、そのチップだけ縦に伸びて不揃いになるため、**「...」で省略する（ellipsis）方式に変更**した。チップの高さは常に一定に保たれる。省略された場合に備え、`title`属性でフルネームを保持し、ホバー（またはスマホの長押し）で確認できるようにする。

## 14. 複数人がほぼ同時に参加した場合の「接続中→参加確定」処理

Socket.io自体がタイミングを調整するわけではない。各参加者は独立したイベントとして扱われるため、フロントエンドが**参加者IDをキーにしてチップを管理**していれば、同時に何人参加しても取り違えは起きない（名前だけで管理すると同姓の参加者などで事故りうるため、必ずID基準にする）。特別な同時参加対応ロジックは不要。
