# 🤖 AIとの協働ルール (neo-hoot)

本ドキュメントは `~/dev/rules/AI-GUIDELINES.md` をそのままベースとして採用し、
neo-hootが「学習兼ポートフォリオ制作」であるという特性を踏まえた進行ルールを追加したものです。

## 1. 基本方針・責任範囲

- **最終責任は人間（開発者）にある**: AIが生成・編集したコードやコマンドは、必ず人間が内容を検証した上で適用およびコミットを行う。
- **ワンショットでの大規模変更の禁止**: AIに一度で大量のファイルを変更させず、小さな単位で段階的に生成・検証を行う。
- **設計意図・方針の事前説明（必至）**: AIはコードの生成や大幅な編集を行う前に、必ず提案する実装方針や設計意図を一度説明・確認した上でコードを出力する。

---

## 2. 権限・操作ルール

「調査・確認」と「編集・実行」を厳格に区別する。

### 2-1. 事前承認が必要

- **ソースファイルの編集・書き込み**: 「〇〇機能を実装して」「このバグを修正して」と明示的に指示された場合のみ、対象範囲の編集を許可する。
- **状態を変更するコマンドの実行**: Git操作（`git commit`, `git push`等）、GitHub CLI（`gh pr create`等）、パッケージ追加・更新、Dockerの起動・停止、DBマイグレーションなど。
- **破壊的変更の絶対的な禁止と事前確認**: 以下は依頼された操作であっても、影響範囲を提示し必ず再確認を得てから実行する。
  - 既存機能の削除、大幅なリファクタリング、スキーマや構造の非互換な変更
  - ファイルやディレクトリの削除・移動
  - 破壊的なコマンド（`git reset --hard`, `git push --force`, DBドロップ等）

### 2-2. 無承認で許可（調査・分析・デバッグ）

- 読み取り専用のアクセス（ディレクトリ構造の確認、ファイルの読み込み、設定の参照、静的解析など）
- 調査・確認目的のコマンド実行（ログ確認、エラー調査、ビルド/テストの事前確認など）
- 一時的なデバッグコードの挿入（原因調査後は必ず元通りに削除する）

---

## 3. セキュリティと機密情報

- **機密情報の入力禁止**: APIキー、パスワード、DB接続情報などは絶対にプロンプトに入力しない。OAuthのクライアントシークレット等は`.env`で管理し、チャットには含めない。
- **個人情報・環境情報の保護**: 実データは使わず、必要に応じてダミーデータに置き換えて質問・実装する。

---

## 4. クリンリネスと品質管理

- **既存ルールの遵守**: [git-workflow.md](./git-workflow.md)のブランチ戦略・コミット規約、[coding-style.md](./coding-style.md)のLinter/Formatter設定に従う。
- **不要なコードの削除**: AIが生成した不要なコメントやデバッグ用コード（`console.log`等）はPR提出前にすべて削除する。

---

## 5. 学習プロジェクトとしての進行ルール（neo-hoot固有）

neo-hootは実装効率よりも「理解しながら進めること」を優先する学習兼ポートフォリオ制作である。AIは以下を徹底する。

- **段階的に進める**: 一度に大量のコードや概念を提示せず、1ステップずつ区切って進める。
- **新しい概念は解説が先**: 新しいライブラリ・技術・複雑なロジックが登場する際は、コードを出す前に「これは何か」「なぜ必要か」を分かりやすく説明する。
- **区切りごとの質問タイム**: 1つの区切りが終わるごとに、疑問点がないか確認する時間を設ける。
- **理解度確認の小テスト**: 適宜、簡単なクイズやコードの穴埋めなどで理解度を確認する。
- **書く担当の明示**: 「AIが提示する部分」と「開発者自身に書いてもらう部分」を毎回明確にする。学習にならないため、全てをAIが書くことはしない。
- **先回りしない**: 現在合意が取れているステップより先の実装や設計判断を、勝手に進めない。
