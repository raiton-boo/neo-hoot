# 🎨 デザインシステム (neo-hoot)

ネオブルータリズム（POP寄り）のデザイン言語を定義する。ここで決めた内容を元に`docs/wireframes/`でワイヤーフレームを作成し、実装時は`apps/web`のTailwind設定に反映する。

**画面ごとの詳細な挙動・デザイン上の判断は、このファイルではなく個別のドキュメントに分離している。** このファイルには、複数画面にまたがる共通のルール（配色・タイポグラフィ・コンポーネントの基本ルールなど）のみを記載する。個別画面のドキュメントは11節を参照。

## 1. ネオブルータリズムとは・今回の方向性

ネオブルータリズムは、太い枠線・ずれたベタ塗りの影（ぼかしなし）・高彩度の色面を特徴とするデザインスタイル。「あえて洗練させすぎない」荒削りな存在感が特徴。

今回は**POP寄り**（コントラストの強い原色系だが、遊び心のある明るい配色、角を少し丸めた親しみやすさ）に振る。完全な無彩色・鋭角のみのストイックな方向にはしない。

## 2. カラーパレット

### ライトモード（デフォルト）

| 用途                   | 変数名              | 値                              |
| :--------------------- | :------------------ | :------------------------------ |
| 背景                   | `--color-bg`        | `#FFFBEA`（生成り・クリーム色） |
| サーフェス（カード等） | `--color-surface`   | `#FFFFFF`                       |
| 枠線・文字             | `--color-ink`       | `#0A0A0A`                       |
| プライマリ（黄）       | `--color-primary`   | `#FFD60A`                       |
| セカンダリ（ピンク）   | `--color-secondary` | `#FF3D8A`                       |
| アクセント（青）       | `--color-accent`    | `#3D5AFF`                       |
| 成功（緑）             | `--color-success`   | `#00C853`                       |
| 危険（赤）             | `--color-danger`    | `#FF3B30`                       |

### ダークモード

| 用途                 | 変数名            | 値                                                       |
| :------------------- | :---------------- | :------------------------------------------------------- |
| 背景                 | `--color-bg`      | `#16121F`（ネイビー寄りの濃紫）                          |
| サーフェス           | `--color-surface` | `#221C33`                                                |
| 枠線・文字           | `--color-ink`     | `#F5F5F0`                                                |
| その他のアクセント色 | —                 | ライトモードと同じ値を使用（十分な彩度・明度があるため） |

ニュートラルなグレー（`#121212`系）や漆黒（`#0A0A0A`系）も候補として比較したが、POP寄りのネオブルータリズムという方向性には「ネイビー」が最も合っていたため採用した。

## 3. タイポグラフィ

- **見出し（英数字）**: `Paytone One`。丸みがあり親しみやすい、POP寄りのネオブルータリズムに合う極太の見出し用フォント。
- **見出し（日本語）**: 別途、太めの日本語フォント（例: `Noto Sans JP` Bold）を組み合わせる。`Paytone One`は欧文専用のため、日本語部分では反映されない。
- **本文**: 可読性重視のサンセリフ体（例: `Inter`、またはシステムフォント）。
- 見出しは基本**大きく・太く**、余白を詰め気味にしてインパクトを出す。

候補として`Space Grotesk`, `Fredoka`, `Titan One`, `Luckiest Guy`, `Bangers`も比較したが、POPさと視認性のバランスから`Paytone One`を採用した。

## 4. コンポーネントの基本ルール

| 要素                       | ルール                                                                                                    |
| :------------------------- | :-------------------------------------------------------------------------------------------------------- |
| **枠線**                   | `3px solid var(--color-ink)`。細い枠線は使わない。                                                        |
| **影**                     | ぼかしなしのオフセット影: `4px 4px 0 var(--color-ink)`。光源を意識したリアルな影ではなく、記号的な影。    |
| **角丸**                   | `8px`〜`12px`程度の控えめな丸み（完全な鋭角にはしない。POP寄りのため）。                                  |
| **押下時のフィードバック** | ボタン等を押した際、影を`2px 2px 0`に縮めつつ要素を`2px, 2px`分ずらす。「実際に沈み込んだ」ように見せる。 |
| **色の塗り方**             | グラデーション・半透明は使わない。ベタ塗りのみ。                                                          |

## 5. ダークモードの切り替え方針

- OSの設定（`prefers-color-scheme`）に追従することを基本としつつ、ユーザーが手動で切り替えられるトグルも用意する。
- 色の意味（プライマリ＝黄、成功＝緑、など）はライト/ダークで変えない。背景・枠線・文字色のみ反転させる。

## 6. アクセシビリティ上の注意

- 色だけで正誤を伝えない（アイコンや文言も併用する）。参加者が回答の正誤を確認する画面などで特に注意する。
- 枠線・影を多用するデザインのため、コントラスト比は自然に確保しやすいが、パステルカラーは使わず、彩度・明度のはっきりした色のみを採用する。

## 7. テキストの省略ルール（ニックネーム等、長さが不定な文字列全般）

ニックネームのように、ユーザーが自由に入力できる文字列は、長さの上限を設けていても表示欄に収まらない場合がある。以下を全画面共通のルールとする。

- 表示欄に収まらない場合は、**折り返さずに`...`で省略する**（`text-overflow: ellipsis` + `white-space: nowrap` + `overflow: hidden`）。折り返すと、その要素だけ縦に伸びて周囲の見た目が崩れるため。
- 省略された場合に備え、**要素には必ず`title`属性でフルの文字列を保持する**。ホバー（PCの場合）や長押し（スマートフォンの場合）で確認できるようにする。
- flexアイテム内でこれを効かせる場合は、対象要素に`min-width: 0`も併せて指定する（flexboxはデフォルトで内容物の最小幅を確保しようとし、`text-overflow`が効かないことがあるため）。

## 8. 実装時のTODOメモ（全画面共通）

- **参加⇔ホスト切り替えのアニメーション**: `docs/wireframes/`のワイヤーフレームでは簡易的なCSSアニメーション（登場時のフェード＋スライド）のみ。本実装（`apps/web`）では`Framer Motion`の`AnimatePresence`を使い、タブ切り替え時にもっと滑らかな遷移（クロスフェードやスライド）を実装する。（該当: `participant/join.md`, `host/login.md`）
- **共通ヘッダーのユーザーメニュー**: PC/スマートフォンでの挙動・デザインは未確定（例: PCはホバーで開くドロップダウン、スマホはタップでボトムシート等）。実装フェーズで改めて決める。（該当: `host/dashboard.md`）
- **参加用URLのハードコード禁止**: ワイヤーフレームでは`neo-hoot.app/join`という文字列を直接書いているが、これは環境（ローカル開発・本番等）によって実際のドメインが変わる。本実装では`window.location.origin`など、実行時の環境から動的に取得した値を表示する（`coding-style.md`の「機密情報・環境依存値のハードコード禁止」の方針にも合わせる）。

## 9. 共通ヘッダー（`.app-header`）を入れる画面の方針

- **入れる（管理画面系）**: クイズ一覧、クイズ編集など、ホストが自分のペースで操作する画面
- **入れない（ライブ進行画面）**: ロビー、出題中、設問結果、最終結果など、プロジェクター等に映して参加者全員が見る画面。ホスト個人のナビゲーション要素は不要かつ邪魔になるため、最小限の表示にする

## 10. 共通UIコンポーネント候補（実装フェーズで検討）

ワイヤーフレームを作る中で、複数画面で似た役割を持つパーツがいくつか見つかった。実装時にReactコンポーネントとして共通化するかどうかは、そのフェーズで改めて判断する。

- **「〇〇を待っています」系のステータス表示**（パルスドット＋文言）: ホストの`lobby.html`（「参加者を待っています」）と参加者の`lobby-wait.html`（「ホストが開始するまでお待ちください」）。文言はそれぞれの立場で異なるが、視覚的なパターン（パルスドット＋テキスト）は共通化できそうな候補。
